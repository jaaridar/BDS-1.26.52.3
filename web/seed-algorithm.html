1. The algorithm, completely

Bedrock's structure placement answers one question: given a 64-bit world seed, which chunks contain the start of structure set S? It does it in two stages — a candidate grid, which is pure arithmetic, and a per-structure gate, which asks the world's biome and height data whether the candidate is allowed. The grid is fully recovered. The gate is recovered only for strongholds, and for the rest the model reproduces every captured answer anyway, because the gate rejects candidates rather than moving them.

1.1 Coordinates and the seed reduction

Two coordinate systems are in play and they are never mixed: chunks (16 blocks) and blocks. A structure start is computed in chunks and reported as the block at the chunk's centre, chunk × 16 + 8. Cell indices are floor(chunk ÷ spacing), with Java's floor (towards negative infinity), not truncation.

A world seed is 64 bits, and the two placement engines read different parts of it:

seed32 = low 32 bits of the seed (mod 2^32, two's complement) seed48 = low 48 bits of the seed (mod 2^48) The Mersenne engine folds its cell seed into 32 bits, so it sees only seed32. The Java engine masks its LCG state to 48 bits, so it sees only seed48.

Consequence, measured: seeds s and s + 232 place every Mersenne-engine set identically, and seeds s and s + 248 place every Java-engine set identically. The self-checks below re-derive this on your machine rather than asking you to believe it.

1.2 The Mersenne stream

Both engines start from a Mersenne Twister seeded with init_genrand: 624 words of state, multiplier 1812433253, tempering masks 0x9d2c5680 and 0xefc60000. The two draw conventions are not part of the published algorithm, so they were measured rather than assumed:

next32() = one tempered 32-bit word nextInt(bound) = next32() mod bound (unsigned divide, no rejection) nextUnit() = f32( next32() × 2^-32 ) (integer → double → float)

The f32 narrowing matters: the gate compares against 0.25f, and a value a whisker above 0.25 can round down onto it. That case is implemented exactly, not approximately.

1.3 The candidate grid

Every set except strongholds uses the same resolver, with per-set numbers. A cell is spacing chunks wide and its candidate sits at least separation chunks inside it, so span = spacing − separation.

cellX = floor(chunkX ÷ spacing) cellZ = floor(chunkZ ÷ spacing) span = spacing − separation Mersenne engine: cellSeed = (cellX × 0x9939f508 + cellZ × 0xf1565bd5 + seed32 + salt) mod 2^32 state = MT19937(cellSeed) linear ox = next32() mod span oz = next32() mod span triangular ox = floor( (next32() mod span + next32() mod span) ÷ 2 ) oz = floor( (next32() mod span + next32() mod span) ÷ 2 ) Java engine: cellSeed = (cellX × 341873128712 + cellZ × 132897987541 + seed48 + salt) mod 2^64 state = (cellSeed XOR 0x5deece66d) mod 2^48 next(b) = state = (state × 0x5deece66d + 0xb) mod 2^48; return state ≫ (48 − b) linear ox = nextInt(span) oz = nextInt(span) triangular ox = floor( (nextInt(span) + nextInt(span)) ÷ 2 ) (same for z) start chunk = (cellX × spacing + ox, cellZ × spacing + oz) start block = (startChunkX × 16 + 8, startChunkZ × 16 + 8)

The two 32-bit multipliers are the low halves of the Java constants (341873128712 mod 2^32 = 0x9939f508, 132897987541 mod 2^32 = 0xf1565bd5): the binary multiplies in 32 bits, which is exactly a fold of the 64-bit mix.

1.4 Strongholds

Strongholds are not a ring walk in this build, and they are not jittered inside a cell. They sit on a 200-chunk grid, each cell carrying one stronghold, and the mix runs over the cell's centre rather than its index:

u = cellX × 200 + 100 v = cellZ × 200 + 100 cellSeed = (u × 0x9babeb51 + v × 0xbe68aeb9 + seed32 + 0x5d534e7) mod 2^32 state = MT19937(cellSeed) dx = next32() mod 100 dz = next32() mod 100 gate = f32( next32() × 2^-32 ) gridChunk = (cellX × 200 + 50 + dx, cellZ × 200 + 50 + dz)

The third draw is a gate, compared against 0.25, and what it decides is measured rather than assumed: it decides whether the stronghold ends up on that grid position. Every cell carries exactly one stronghold — no capture has ever shown two in one cell — but when the gate fails, the generator moves the stronghold, and the moved position comes out of a biome query that is not modelled here.

The capture corpus is not present in this build, so no tally is quoted here.

There is a second population of strongholds that this grid cannot express: every world also contains exactly three strongholds at villages, at radii of 47 to 662 chunks from the origin. Their positions are exact, because they are village chunks and the village grid is exact — but which villages are chosen is not recovered, so they are listed as open below and are not reported by the calculator.

1.5 What a locate answer is

/locate structure walks cells outward from your position and returns the first candidate whose biome and height checks pass, with its distance. It does not enumerate and it does not sort globally, which is why two different origins can return two different "nearest" answers for the same structure. The model here reports the candidate grid, so it reproduces locate exactly when the accepted candidate is the grid candidate — which is the case for every captured answer of every set offered as a filter.

6. Forensic record: how each number was pinned

6.1 Method

Two independent sources were used, and a constant was only accepted when both agreed:

  1. Static: the shipped bedrock_server (Linux x86-64, version 1.26.52.3) was disassembled. Constants were read out of the instruction stream and the read-only section, and the call graph around the structure feature was mapped. Addresses are cited below so any reader can check them with objdump — nothing else here depends on trusting this paragraph.
  2. Dynamic: a real server, started once per seed, was asked /locate structure from a scripted set of origins. The answers are recorded with the seed they came from (research/proprietary/bds-1.26.52.3/structures/captures/, 1411 files) and replayed by the verifiers. A parameter set was accepted only when it reproduced every captured position of that set; a fit that needed a tolerance to reach a neighbouring chunk is reported as exactly that.

8. What is still open

  • Which villages carry the three strongholds. The positions are known (they are village chunks) and the count is known (exactly three per world), but the selection is not recovered: it is not a per-village random draw, not a nearest-village snap, not a rank cut, and not tied to the gated cells. It reads more of the seed than the grid does, which points at the biome layer — the same query that relocates the ungated cells. Everything ruled out is in §7 with its number.
  • 19 of the 510 gated strongholds. The gate is necessary and 96.3% sufficient; the remainder are cells the generator moved for a non-gate reason. They are reported as gated with a flag, never as exact.
  • Biomes and terrain. The climate noise router has not been recovered, so no surface biome, height or block can be predicted from a seed. The biome data — 76 biomes with their climate targets — is read from the packs, but data is not a sampler, which is why there is no biome filter in §4.
  • Seven sets with unmeasured placement: ocean ruins, desert pyramids, jungle temples, witch huts, igloos, mineshafts and abandoned camps. Their parameters are placeholders or their gate is a per-chunk probability whose threshold is unknown.
  • Obsidian and the rest of the structure itself. This file covers where a structure starts. Piece layout, jigsaw assembly, loot tables and block placement are separate systems and are not modelled.

Appendix A — the code, verbatim

This is the implementation the calculators above actually run — inlined unmodified from the repository (the sha256 of each file is in §10). The JavaScript below is the reference implementation; the WebAssembly core is a transcription of it, and §5 compares the two.

src/world/mt19937.js — MT19937 and its draw conventions 
'use strict'

/**
 * Deterministic Mersenne Twister (MT19937), the generator BDS seeds for chunk
 * terrain and for every noise layer.
 *
 * Clean-room implementation from the published MT19937 definition
 * (Matsumoto & Nishimura, 1997): 624-word state, 32-bit words, tempering
 * constants 0x9d2c5680 / 0xefc60000, initialiser multiplier 1812433253.
 *
 * Two of the draw conventions are not fixed by the algorithm itself -- the
 * binary calls through a virtual interface, so "next float" and "next int in
 * [0, bound)" are implementation choices. Both are policy objects here so a
 * caller can select an interpretation instead of hard-coding a guess, and
 * `tools/worldgen-golden` can score the alternatives against real server
 * output.
 */

/** Smallest float below 1 that a 24-bit draw can produce, as a double. */
const INV_2_24 = 2.3283064365386963e-10
/** 2^-32, the scale the binary applies to a full 32-bit draw. */
const INV_2_32 = 2.3283064365386963e-10
/** 2^-53, the scale of a 53-bit draw. */
const INV_2_53 = 1.1102230246251565e-16

const N = 624
const M = 397
const MATRIX_A = 0x9908b0df
const UPPER_MASK = 0x80000000
const LOWER_MASK = 0x7fffffff
const TEMPER_MASK_B = 0x9d2c5680
const TEMPER_MASK_C = 0xefc60000
const INIT_MULT = 1812433253

class Mt19937 {
  constructor (seed) {
    this.state = new Uint32Array(N)
    this.index = N
    this.seed(seed)
  }

  /** init_genrand: state[0] = seed, state[i] = f(state[i-1]) + i. */
  seed (seed) {
    this.state[0] = seed >>> 0
    for (let i = 1; i < N; i++) {
      const prev = this.state[i - 1]
      this.state[i] = (Math.imul(prev ^ (prev >>> 30), INIT_MULT) + i) >>> 0
    }
    this.index = N
  }

  /** Produce the next block of 624 words. */
  generate () {
    const s = this.state
    for (let i = 0; i < N; i++) {
      const y = (s[i] & UPPER_MASK) | (s[(i + 1) % N] & LOWER_MASK)
      let next = s[(i + M) % N] ^ (y >>> 1)
      if (y & 1) next ^= MATRIX_A
      s[i] = next >>> 0
    }
    this.index = 0
  }

  /** Raw 32-bit output word, tempered. */
  nextU32 () {
    if (this.index >= N) this.generate()
    let y = this.state[this.index++]
    y ^= y >>> 11
    y ^= (y << 7) & TEMPER_MASK_B
    y ^= (y << 15) & TEMPER_MASK_C
    y ^= y >>> 18
    return y >>> 0
  }

  /**
   * A real in [0, 1).
   *
   * 'u32' is the measured convention: one word, widened to a double, scaled by
   * 2^-32, then narrowed to float. That is exactly the binary's sequence
   * `MOV EAX,EAX / CVTSI2SD / MULSD 2^-32 / CVTSD2SS`, so the value carries
   * full 32-bit granularity before the float rounding.
   *
   * The other entries are kept as alternatives for fitting, not as guesses:
   * 'float24' is a 24-bit float canonical draw, 'double53' a 53-bit double one.
   */
  nextUnit (policy) {
    if (policy !== 'float24' && policy !== 'double53') {
      // Default and measured: 32 bits through double, narrowed to float.
      return Math.fround(this.nextU32() * INV_2_32)
    }
    if (policy === 'double53') {
      const hi = this.nextU32() >>> 5
      const lo = this.nextU32() >>> 6
      return (hi * 67108864 + lo) * INV_2_53
    }
    return (this.nextU32() >>> 8) * INV_2_24
  }

  /**
   * A uniform integer in [0, bound).
   *
   * 'modulo' is the measured convention: the binary issues an unsigned
   * `DIV`, i.e. `raw32 % bound`, with no rejection. The others are fit
   * candidates ('topBits' high-bit masking, 'reject' Lemire multiply-shift).
   */
  nextInt (bound, policy) {
    if (bound <= 1) {
      this.nextU32()
      return 0
    }
    if (policy === 'modulo') return this.nextU32() % bound
    if (policy === 'reject') {
      // Threshold trick: reject the values that would make the low part wrap.
      const threshold = (2 ** 32 - bound) % bound
      for (;;) {
        const r = this.nextU32()
        const product = r * bound
        if (product % 2 ** 32 >= threshold) return Math.floor(product / 2 ** 32)
      }
    }
    // 'topBits': mask off enough high bits; exact for powers of two.
    const bits = 32 - Math.clz32(bound - 1)
    const mask = (1 << bits) - 1
    for (;;) {
      const candidate = this.nextU32() >>> (32 - bits)
      if (candidate <= mask && candidate < bound) return candidate
    }
  }
}

'use strict'

/**
 * The 48-bit linear congruential generator behind structure placement.
 *
 * Recovered from the binary: `br::worldgen::WorldGenRandom` implements the
 * classic `next(bits)` loop with multiplier 0x5deece66d and addend 0xb, masked
 * to 48 bits, and its seed is `(seed ^ 0x5deece66d) & 0xffffffffffff`
 * (research/proprietary/bds-1.26.52.3/ANALYSIS.md section 4.4, function
 * 0xd2d59a0).
 *
 * State is held in a BigInt so the 48-bit arithmetic cannot silently lose
 * precision the way doubles would.
 */

const MULTIPLIER = 0x5deece66dn
const ADDEND = 0xbn
const MASK = 0xffffffffffffn
const DOUBLE_UNIT = 1.1102230246251565e-16 // 2^-53

class JavaRandom {
  constructor (seed = 0n) {
    this.setSeed(seed)
  }

  /** Seeds the stream. Accepts a BigInt, a number, or a numeric string. */
  setSeed (seed) {
    const value = typeof seed === 'bigint' ? seed : BigInt(seed)
    // Java truncates the incoming long into 48 bits after the xor.
    this.state = (value ^ MULTIPLIER) & MASK
  }

  /** The raw next(bits) step: the primitive every other method builds on. */
  next (bits) {
    this.state = (this.state * MULTIPLIER + ADDEND) & MASK
    const shifted = this.state >> BigInt(48 - bits)
    return Number(shifted)
  }

  /** Uniform int in [0, bound). Rejection loop, as in the original. */
  nextInt (bound) {
    if (bound === undefined) {
      const high = this.next(32)
      // next(32) yields an unsigned 32-bit value; the reference returns int32.
      return high | 0
    }
    if (!Number.isInteger(bound) || bound <= 0) {
      throw new RangeError(`bound must be a positive integer, got ${bound}`)
    }
    if ((bound & -bound) === bound) {
      // Power of two: the reference still draws 31 bits and scales them down,
      // so the stream advances by exactly one step here.
      return Number((BigInt(bound) * BigInt(this.next(31))) >> 31n)
    }
    let bits
    let value
    do {
      bits = this.next(31)
      value = bits % bound
    } while (bits - value + (bound - 1) < 0)
    return value
  }

  /**
   * A full 64-bit draw, exactly as the reference does it:
   * `((long) next(32) << 32) + next(32)` with *signed* halves, so the low word
   * can borrow from the high one.
   */
  nextLong () {
    const high = this.next(32) | 0
    const low = this.next(32) | 0
    return BigInt(high) * 4294967296n + BigInt(low)
  }

  /** Uniform float in [0, 1). */
  nextFloat () {
    return this.next(24) / (1 << 24)
  }

  /** Uniform double in [0, 1). */
  nextDouble () {
    const high = this.next(26)
    const low = this.next(27)
    return (high * 134217728 + low) * DOUBLE_UNIT
  }

  /** True with probability `frequency`. */
  nextChance (frequency) {
    return this.nextFloat() < frequency
  }
}

/** Multipliers the binary uses to fold grid coordinates and a set salt in. */
const X_MULTIPLIER = 341873128712n
const Z_MULTIPLIER = 132897987541n

/**
 * The structure seed for one grid cell.
 *
 * Recovered verbatim from the spacing resolver (`0xd2d2570`):
 * `x * 341873128712 + z * 132897987541 + seed + salt`, then seeded into the
 * LCG. Java long arithmetic wraps, so the sum is taken modulo 2^64 first.
 */
function structureSeed (seed, cellX, cellZ, salt) {
  let sum = BigInt(cellX) * X_MULTIPLIER + BigInt(cellZ) * Z_MULTIPLIER
  sum += BigInt(seed) + BigInt(salt)
  // Two's complement wrap into a signed 64-bit value.
  sum &= 0xffffffffffffffffn
  if (sum >= 0x8000000000000000n) sum -= 0x10000000000000000n
  return sum
}

src/world/structure-placement.js — the candidate grid 
'use strict'

/**
 * Structure placement: turning a seed into structure positions.
 *
 * The pipeline was recovered from the binary and then confirmed against the
 * server, and it is shorter than the Java one it borrows its constants from:
 *
 *   1. the world is cut into cells of `spacing` chunks (cell = floor(chunk / spacing));
 *   2. a cell's seed is
 *        seed32 = cellX * 341873128712 + cellZ * 132897987541 + seed + salt
 *      evaluated mod 2^32 (multiproperties of the Java constants folded down);
 *   3. that seed initialises a 32-bit Mersenne Twister (init_genrand);
 *   4. the Mersenne stream picks the offset inside the cell:
 *        linear      one  draw per axis:  next32() % span
 *        triangular  two draws per axis:  (next32() % span + next32() % span) / 2
 *      with span = spacing - separation;
 *   5. the start chunk is cell * spacing + offset, i.e. it is always inside its
 *      own cell and never inside the separation margin;
 *   6. optional per-cell odds gate drawn from the same stream.
 *
 * Two engines exist in the shipped binary, and which one a set uses is
 * measured, not assumed:
 *
 *   'mt'    the legacy (hard-coded) structure sets. Seven of them reproduce
 *           every captured position exactly (see tools/worldgen-algo/verify-placements.js).
 *   'java'  the data-driven sets that come out of the vanilla packs. These use
 *           a Java-compatible 48-bit LCG over the same cell seed, computed in
 *           64 bits. Their reported position is the structure's own origin
 *           block, which sits in the placement chunk or one chunk before it.
 *
 * Everything above is transcribed from the disassembly. The per-structure
 * numbers -- spacing, separation, salt, spread type, engine -- are data the
 * engine supplies; they live in `structures-data.js` and are confirmed by the
 * oracle, so they are never invented here.
 */

const { Mt19937 } = require('./mt19937')
const { JavaRandom } = require('./java-random')

/** Java's placement constants, which the binary folds into 32-bit form. */
const CELL_MUL_X = 341873128712n
const CELL_MUL_Z = 132897987541n

/** The same two constants reduced to what a 32-bit multiply sees. */
const CELL_MUL_X32 = Number(CELL_MUL_X % 4294967296n) >>> 0 // 0x9939f508
const CELL_MUL_Z32 = Number(CELL_MUL_Z % 4294967296n) >>> 0 // 0xf1565bd5

/** Floor division that matches Java's for negative numerators. */
function floorDiv (a, b) {
  return Math.floor(a / b)
}

/**
 * A world seed reduced to the 32 bits the Mersenne cell seed folds in.
 *
 * Seeds above 2^53 are legal (`-9223372036854775808` is a real world seed) and
 * `Number(seed) >>> 0` reduces *those* incorrectly: it rounds to the nearest
 * double first, so 2^63 - 1 arrives as 2^63 and reduces to 0 instead of
 * 0xffffffff. The reduction therefore goes through BigInt whenever the seed is
 * not a safe integer. Verified by `test/unit/world-placement-seed-width.test.js`:
 * seed 2^63 - 1 must place structures exactly like seed -1.
 */
function seed32 (seed) {
  if (typeof seed === 'bigint') return Number(BigInt.asUintN(32, seed))
  if (typeof seed === 'string') return Number(BigInt.asUintN(32, BigInt(seed.trim())))
  if (Number.isSafeInteger(seed)) return Number(BigInt.asUintN(32, BigInt(seed)))
  return Number(BigInt.asUintN(32, BigInt(Math.trunc(seed))))
}

/** The low 48 bits, which is all the Java engine's LCG keeps. */
function seed48 (seed) {
  if (typeof seed === 'bigint') return BigInt.asUintN(48, seed)
  if (typeof seed === 'string') return BigInt.asUintN(48, BigInt(seed.trim()))
  if (Number.isSafeInteger(seed)) return BigInt.asUintN(48, BigInt(seed))
  return BigInt.asUintN(48, BigInt(Math.trunc(seed)))
}

/**
 * The 32-bit cell seed the Mersenne engine consumes.
 *
 * The binary computes `cellZ * -0xea9a42b + cellX * -0x66c60af8 + salt + seed`
 * in 32-bit two's complement; the two magnitudes are exactly the low halves of
 * the Java constants above. Only the low 32 bits of the world seed take part,
 * which is why seeds 1 and 4294967297 share placements but not biomes.
 */
function cellSeed (seed, cellX, cellZ, salt) {
  return (Math.imul(cellX, CELL_MUL_X32) +
    Math.imul(cellZ, CELL_MUL_Z32) +
    seed32(seed) +
    (Number(salt) >>> 0)) >>> 0
}

/** The same cell seed kept at 64 bits, which is what the Java engine sees. */
function javaCellSeed (seed, cellX, cellZ, salt) {
  return BigInt.asIntN(64,
    BigInt(cellX) * CELL_MUL_X +
    BigInt(cellZ) * CELL_MUL_Z +
    BigInt(seed) +
    BigInt(salt))
}

/** The inside-a-cell width: the offset is drawn from [0, span). */
function spanOf (placement) {
  const span = placement.spacing - placement.separation
  if (span <= 0) {
    throw new RangeError(`${placement.id}: spacing ${placement.spacing} leaves no room inside separation ${placement.separation}`)
  }
  return span
}

/** Offset inside one cell, for the Mersenne engine. */
function offsetMt (random, span, triangular) {
  if (!triangular) {
    return [random.nextInt(span, 'modulo'), random.nextInt(span, 'modulo')]
  }
  const x = (random.nextInt(span, 'modulo') + random.nextInt(span, 'modulo'))
  const z = (random.nextInt(span, 'modulo') + random.nextInt(span, 'modulo'))
  return [Math.floor(x / 2), Math.floor(z / 2)]
}

/** Offset inside one cell, for the Java engine. */
function offsetJava (random, span, triangular) {
  if (!triangular) {
    return [random.nextInt(span), random.nextInt(span)]
  }
  const x = random.nextInt(span) + random.nextInt(span)
  const z = random.nextInt(span) + random.nextInt(span)
  return [Math.floor(x / 2), Math.floor(z / 2)]
}

/**
 * Where one grid cell puts its structure.
 *
 * @param {object} placement {spacing, separation, salt, spreadType, engine, frequency}
 * @param {number} seed world seed
 * @param {number} cellX cell coordinate (chunk / spacing, floored)
 * @param {number} cellZ
 * @returns {{chunkX: number, chunkZ: number, accepted: boolean}}
 */
function structureInCell (placement, seed, cellX, cellZ) {
  const span = spanOf(placement)
  const triangular = placement.spreadType === 'triangular'
  const engine = placement.engine === 'java' ? 'java' : 'mt'
  let offsets
  let gate = null
  if (engine === 'java') {
    const random = new JavaRandom(javaCellSeed(seed, cellX, cellZ, placement.salt))
    offsets = offsetJava(random, span, triangular)
    gate = random
  } else {
    const random = new Mt19937(cellSeed(seed, cellX, cellZ, placement.salt))
    offsets = offsetMt(random, span, triangular)
    gate = random
  }
  // The frequency gate, when a set declares one, is drawn from the same stream
  // after the offsets -- the order matters, so it is kept explicit.
  let accepted = true
  if (placement.frequency !== undefined && placement.frequency < 1) {
    accepted = engine === 'java'
      ? gate.nextFloat() < placement.frequency
      : gate.nextUnit() < placement.frequency
  }
  return {
    chunkX: cellX * placement.spacing + offsets[0],
    chunkZ: cellZ * placement.spacing + offsets[1],
    accepted
  }
}

/**
 * Every accepted cell start within `radiusChunks` of a chunk.
 *
 * Cells are visited in a deterministic order so callers can rely on the result
 * being reproducible; the order is by distance, then by cell coordinates.
 */
function candidateStarts (placement, seed, chunkX, chunkZ, radiusChunks) {
  const minCellX = floorDiv(chunkX - radiusChunks, placement.spacing) - 1
  const maxCellX = floorDiv(chunkX + radiusChunks, placement.spacing) + 1
  const minCellZ = floorDiv(chunkZ - radiusChunks, placement.spacing) - 1
  const maxCellZ = floorDiv(chunkZ + radiusChunks, placement.spacing) + 1
  const out = []
  for (let cellZ = minCellZ; cellZ <= maxCellZ; cellZ++) {
    for (let cellX = minCellX; cellX <= maxCellX; cellX++) {
      const start = structureInCell(placement, seed, cellX, cellZ)
      if (!start.accepted) continue
      const blockX = start.chunkX * 16 + 8
      const blockZ = start.chunkZ * 16 + 8
      const distance = Math.hypot(blockX - (chunkX * 16 + 8), blockZ - (chunkZ * 16 + 8))
      if (distance > radiusChunks * 16) continue
      out.push({ ...start, cellX, cellZ, blockX, blockZ, distance })
    }
  }
  out.sort((a, b) => a.distance - b.distance || a.cellX - b.cellX || a.cellZ - b.cellZ)
  return out
}

/**
 * The nearest candidate start, i.e. what `locate structure` would report before
 * the per-structure biome and height checks are applied.
 *
 * This is the *candidate grid*, not the answer: the server walks the same cells
 * in ring order around the origin and returns the first one whose biome and
 * height pass, so a caller that does not model biomes yet can only offer the
 * cell grid.
 */
function nearestStart (placement, seed, chunkX, chunkZ, radiusChunks = 512) {
  const candidates = candidateStarts(placement, seed, chunkX, chunkZ, radiusChunks)
  return candidates.length ? candidates[0] : null
}

module.exports = {
  floorDiv,
  spanOf,
  cellSeed,
  javaCellSeed,
  seed32,
  seed48,
  structureInCell,
  candidateStarts,
  nearestStart,
  CELL_MUL_X,
  CELL_MUL_Z
}
src/world/stronghold.js — the 200-chunk stronghold grid and its gate 
'use strict'

/**
 * Stronghold placement.
 *
 * Strongholds are *not* a ring walk in this build, and they are not a jittered
 * grid of the kind every other structure uses. The 200-chunk cell grid is
 * there, but the cell does not hold a 0..span offset: it holds the *centre* of
 * the cell, and the two salts in the mix are folded over that centre instead of
 * over the cell index. Everything below was read out of the binary and then
 * replayed against captured `locate structure` answers.
 *
 *   cellX = floor(chunkX / 200)                      (chunks, floored)
 *   u     = cellX * 200 + 100                        (the cell centre)
 *   v     = cellZ * 200 + 100
 *   seed32 = u * 0x9babeb51 + v * 0xbe68aeb9 + seed + 0x5d534e7     (mod 2^32)
 *
 * `seed32` seeds a 32-bit Mersenne Twister (the same init_genrand the grid
 * structures use). Three draws come out of it:
 *
 *   draw 1 -> nextInt(100)   the x jitter
 *   draw 2 -> nextInt(100)   the z jitter
 *   draw 3 -> nextUInt() / 2^32, compared against 0.25  (see `gated`)
 *
 * and the grid position of the cell is
 *
 *   chunkX = cellX * 200 + 50 + draw1 % 100
 *   chunkZ = cellZ * 200 + 50 + draw2 % 100
 *
 * What the third draw gates is measured, and it is *not* existence: every cell
 * carries exactly one stronghold (592 captures, no cell holds two). It gates
 * whether the stronghold ends up on that grid position. Across the 592 captured
 * strongholds, 491 sit exactly on the predicted position, every one of those 491
 * is a gated cell, and 0 of the 82 ungated ones are. Of the 510 gated cells, 491
 * are exact -- so the gate is necessary with no counter-example and sufficient
 * 96.3% of the time. The other 19 are cells the generator moved for a reason
 * that is not the gate (the biome query below), which is why `gated` is reported
 * as a flag rather than as a promise of an exact position.
 *
 * A separate probe run asks the server directly about the model's own
 * predictions (`tools/worldgen-algo/verify-probe.js`, 320 probes): 159 of 160
 * gated cells answer with the origin chunk itself, 0 of 160 ungated cells do.
 * Both measurements say the same thing in different directions.
 *
 * The cells that are not exact are relocated: the binary calls a biome provider with
 * the candidate position (`0x4e9fca0`, virtual slot 6 of the object at
 * `+0x1a8`), which can reject the cell or rewrite the position, and the value it
 * leaves behind is what gets re-snapped. That is why relocated strongholds are
 * not on the 200-chunk grid at all -- `(84, 9)` cannot be `cell * 200 + 50 +
 * [0..100)` on either axis. Modelling them needs the biome layer, so this module
 * reports the cell and says `gated: false` rather than inventing a position.
 */

const { Mt19937 } = require('./mt19937')

/** Chunks per stronghold cell. */
const CELL = 200

/** The salt in the stronghold seed mix (`add $0x5d534e7` in the binary). */
const SALT = 0x5d534e7

/**
 * The two multipliers in the seed mix, in the order the binary applies them:
 * the x cell centre is scaled by 0x9babeb51 and the z cell centre by
 * 0xbe68aeb9. They are 32-bit values used with `pmuludq`, not floats, even
 * though the bytes at their addresses also happen to decode as tiny floats.
 */
const MUL_X = 0x9babeb51
const MUL_Z = 0xbe68aeb9

/** The threshold the third draw is compared against (`ucomiss` against 0.25f). */
const GRID_ODDS = 0.25

/**
 * A world seed reduced to the 32 bits the placement mix uses.
 *
 * Seeds go beyond 2^53 in practice (`-9223372036854775808` is a legal world
 * seed), so a `Number(seed) >>> 0` would reduce the wrong value for them. The
 * reduction is therefore done in BigInt whenever the seed is not a safe
 * integer.
 */
function seed32 (seed) {
  if (typeof seed === 'bigint') return Number(BigInt.asUintN(32, seed))
  if (typeof seed === 'string') return Number(BigInt.asUintN(32, BigInt(seed.trim())))
  if (Number.isSafeInteger(seed)) return Number(BigInt.asUintN(32, BigInt(seed)))
  return Number(BigInt.asUintN(32, BigInt(Math.trunc(seed))))
}

/** The centre of a cell, in chunks. */
function cellCentre (cell) {
  return cell * CELL + CELL / 2
}

/** The 32-bit Mersenne seed for one cell. */
function cellSeed (seed, cellX, cellZ) {
  return (Math.imul(cellCentre(cellX), MUL_X) +
    Math.imul(cellCentre(cellZ), MUL_Z) +
    seed32(seed) +
    SALT) >>> 0
}

/**
 * The stronghold a cell carries.
 *
 * @param {number|bigint|string} seed world seed; only its low 32 bits are used,
 *   so seeds 1 and 2^32+1 share every grid position
 * @param {number} cellX cell coordinate, i.e. floor(chunkX / 200)
 * @param {number} cellZ
 * @returns {{cellX: number, cellZ: number, chunkX: number, chunkZ: number,
 *   blockX: number, blockZ: number, gated: boolean, gate: number}}
 *   `chunkX/chunkZ` is the cell's grid position and `gate` its third draw.
 *   When `gated` is false the stronghold exists in this cell but the generator
 *   moved it off that position, so the grid position is not where to dig.
 */
function strongholdInCell (seed, cellX, cellZ) {
  const random = new Mt19937(cellSeed(seed, cellX, cellZ))
  const dx = random.nextInt(100, 'modulo')
  const dz = random.nextInt(100, 'modulo')
  const gate = random.nextUnit()
  const chunkX = cellX * CELL + 50 + dx
  const chunkZ = cellZ * CELL + 50 + dz
  return {
    cellX,
    cellZ,
    chunkX,
    chunkZ,
    blockX: chunkX * 16 + 8,
    blockZ: chunkZ * 16 + 8,
    gated: gate < GRID_ODDS,
    gate
  }
}

/**
 * Every stronghold cell whose grid position is within `radiusChunks` of a
 * chunk, nearest first.
 *
 * The radius test uses the grid position because that is what the cell is
 * anchored to; a relocated stronghold can end up somewhat further out, so a
 * caller matching against real positions should look at the cells around the
 * hits too, not only at the ones inside the radius.
 */
function strongholdsNear (seed, chunkX, chunkZ, radiusChunks = 256) {
  const minCellX = Math.floor((chunkX - radiusChunks) / CELL) - 1
  const maxCellX = Math.floor((chunkX + radiusChunks) / CELL) + 1
  const minCellZ = Math.floor((chunkZ - radiusChunks) / CELL) - 1
  const maxCellZ = Math.floor((chunkZ + radiusChunks) / CELL) + 1
  const out = []
  for (let cellZ = minCellZ; cellZ <= maxCellZ; cellZ++) {
    for (let cellX = minCellX; cellX <= maxCellX; cellX++) {
      const stronghold = strongholdInCell(seed, cellX, cellZ)
      const distance = Math.hypot(stronghold.blockX - (chunkX * 16 + 8),
        stronghold.blockZ - (chunkZ * 16 + 8))
      if (distance > radiusChunks * 16) continue
      out.push({ ...stronghold, distance })
    }
  }
  out.sort((a, b) => a.distance - b.distance || a.cellX - b.cellX || a.cellZ - b.cellZ)
  return out
}

module.exports = {
  CELL,
  SALT,
  MUL_X,
  MUL_Z,
  GRID_ODDS,
  seed32,
  cellCentre,
  cellSeed,
  strongholdInCell,
  strongholdsNear
}

// Seed finder core, compiled to WebAssembly.
//
// This is a *transcription* of the placement rules in `src/world/` (which were
// recovered from the BDS binary and confirmed against the server). The
// JavaScript modules stay the reference implementation: the site loads both and
// the stress test compares them cell by cell, so the two can never drift
// silently. Nothing is invented here -- every constant comes from
// `src/world/structures-data.js` through the generated `placements.gen.ts`, and
// the arithmetic follows the reference line for line.
//
// A search is a list of rules ("at least N of structure X within R chunks, and
// optionally one closer than B blocks"). Each candidate seed is tested rule by
// rule and the first failure stops it, so the order rules are added in is the
// order they cost time.
//
// Only part of a world seed reaches placement, and the two engines differ:
//
//   Mersenne engine  folds the cell seed into 32 bits -> low 32 bits of seed
//   Java engine      masks the LCG state to 48 bits   -> low 48 bits of seed
//
// so the caller passes both reductions and the site can say honestly which
// seeds are distinguishable. See `web/README.md`.

import {
  P_COUNT,
  pSpacing,
  pSeparation,
  pSalt,
  pTriangular,
  pJava
} from './placements.gen'

// ---------------------------------------------------------------------------
// Mersenne Twister (32-bit, init_genrand), exactly as the binary uses it
// ---------------------------------------------------------------------------

const N: i32 = 624
const M: i32 = 397
const MATRIX_A: u32 = 0x9908b0df
const UPPER_MASK: u32 = 0x80000000
const LOWER_MASK: u32 = 0x7fffffff
const TEMPER_B: u32 = 0x9d2c5680
const TEMPER_C: u32 = 0xefc60000
const INIT_MULT: u32 = 1812433253

const mtState = new StaticArray<u32>(N)
let mtIndex: i32 = N
let mtMaterialised: i32 = 0

function mtSeed (seed: u32): void {
  unchecked(mtState[0] = seed)
  for (let i: i32 = 1; i < N; i++) {
    const prev = unchecked(mtState[i - 1])
    unchecked(mtState[i] = (prev ^ (prev >>> 30)) * INIT_MULT + <u32>i)
  }
  mtIndex = 0
  mtMaterialised = 0
}

// One twist step, in place. Doing this lazily lets the few draws placement needs
// skip the other 618 words of the block; the reference regenerates all 624, and
// both orders agree for the first 227 draws, which is every draw used here.
function mtTwist (i: i32): void {
  const y = (unchecked(mtState[i]) & UPPER_MASK) | (unchecked(mtState[(i + 1) % N]) & LOWER_MASK)
  let next = unchecked(mtState[(i + M) % N]) ^ (y >>> 1)
  if ((y & 1) != 0) next ^= MATRIX_A
  unchecked(mtState[i] = next)
  mtMaterialised = i + 1
}

// A tempered word. Cheaper than the reference's "generate a whole block" because
// a search only ever reads a handful of words per seed.
function mtWord (): u32 {
  if (mtIndex >= N) {
    mtIndex = 0
    mtMaterialised = 0
  }
  const i = mtIndex
  if (i >= mtMaterialised) mtTwist(i)
  let y = unchecked(mtState[i])
  mtIndex = i + 1
  y ^= y >>> 11
  y ^= (y << 7) & TEMPER_B
  y ^= (y << 15) & TEMPER_C
  y ^= y >>> 18
  return y
}

// nextUnit(): one word widened to a double, scaled by 2^-32, narrowed to float.
function mtUnit (): f32 {
  return f32(<f64>mtWord() * 2.3283064365386963e-10)
}

// Java-compatible 48-bit LCG, for the data-driven sets
// ---------------------------------------------------------------------------

const JR_MULT: u64 = 0x5deece66d
const JR_ADD: u64 = 0xb
const JR_MASK: u64 = 0xffffffffffff

let jrState: u64 = 0

function jrSeed (seed: i64): void {
  jrState = (<u64>seed ^ JR_MULT) & JR_MASK
}

function jrBits (bits: i32): u32 {
  jrState = (jrState * JR_MULT + JR_ADD) & JR_MASK
  return <u32>(jrState >> <u64>(48 - bits))
}

// nextInt(bound) with the reference's rejection loop and power-of-two path.
function jrInt (bound: i32): i32 {
  if (bound <= 0) return 0
  if ((bound & -bound) == bound) {
    return <i32>((<u64>bound * <u64>jrBits(31)) >> 31)
  }
  let bits: u32 = 0
  let value: u32 = 0
  do {
    bits = jrBits(31)
    value = bits % <u32>bound
  } while (<i32>(bits - value + <u32>(bound - 1)) < 0)
  return <i32>value
}

const CELL_MUL_X: i64 = 341873128712
const CELL_MUL_Z: i64 = 132897987541
const CELL_MUL_X32: u32 = 0x9939f508 // Java constant reduced to 32 bits
const CELL_MUL_Z32: u32 = 0xf1565bd5

function floorDiv (a: i32, b: i32): i32 {
  let q = a / b
  if ((a % b != 0) && ((a < 0) != (b < 0))) q--
  return q
}

function cellSeedMt (seedLo32: u32, cellX: i32, cellZ: i32, salt: u32): u32 {
  const x = unchecked(<u32>cellX * CELL_MUL_X32)
  const z = unchecked(<u32>cellZ * CELL_MUL_Z32)
  return unchecked(x + z + seedLo32 + salt)
}

function cellSeedJava (seedLo48: u64, cellX: i32, cellZ: i32, salt: u32): i64 {
  return (<i64>cellX * CELL_MUL_X) + (<i64>cellZ * CELL_MUL_Z) + (<i64>seedLo48) + (<i64>(<u64>salt))
}

const cellOut = new StaticArray<i32>(2)

// Where one grid cell puts its structure.
function placeInCell (p: i32, seedLo32: u32, seedLo48: u64, cellX: i32, cellZ: i32): void {
  const spacing = pSpacing(p)
  const span = spacing - pSeparation(p)
  let ox: i32 = 0
  let oz: i32 = 0
  if (pJava(p)) {
    jrSeed(cellSeedJava(seedLo48, cellX, cellZ, pSalt(p)))
    if (pTriangular(p)) {
      const x = jrInt(span) + jrInt(span)
      const z = jrInt(span) + jrInt(span)
      ox = x / 2
      oz = z / 2
    } else {
      ox = jrInt(span)
      oz = jrInt(span)
    }
  } else {
    mtSeed(cellSeedMt(seedLo32, cellX, cellZ, pSalt(p)))
    const uSpan = <u32>span
    if (pTriangular(p)) {
      const x = (mtWord() % uSpan) + (mtWord() % uSpan)
      const z = (mtWord() % uSpan) + (mtWord() % uSpan)
      ox = <i32>(x / 2)
      oz = <i32>(z / 2)
    } else {
      ox = <i32>(mtWord() % uSpan)
      oz = <i32>(mtWord() % uSpan)
    }
  }
  unchecked(cellOut[0] = cellX * spacing + ox)
  unchecked(cellOut[1] = cellZ * spacing + oz)
}

// Count starts within radiusChunks of the origin chunk and remember the nearest.
// `stopAt` > 0 lets the caller stop early (then `nearest` is the first found).
function scanPlacement (p: i32, seedLo32: u32, seedLo48: u64, originChunkX: i32, originChunkZ: i32,
  radiusChunks: i32, stopAt: i32): i32 {
  const spacing = pSpacing(p)
  const limit: f64 = <f64>(radiusChunks * 16)
  const originBlockX = originChunkX * 16 + 8
  const originBlockZ = originChunkZ * 16 + 8
  const minCellX = floorDiv(originChunkX - radiusChunks, spacing) - 1
  const maxCellX = floorDiv(originChunkX + radiusChunks, spacing) + 1
  const minCellZ = floorDiv(originChunkZ - radiusChunks, spacing) - 1
  const maxCellZ = floorDiv(originChunkZ + radiusChunks, spacing) + 1
  let count: i32 = 0
  let bestDist: f64 = 1e30
  let bestX: i32 = 0
  let bestZ: i32 = 0
  for (let cellZ = minCellZ; cellZ <= maxCellZ; cellZ++) {
    for (let cellX = minCellX; cellX <= maxCellX; cellX++) {
      placeInCell(p, seedLo32, seedLo48, cellX, cellZ)
      const chunkX = unchecked(cellOut[0])
      const chunkZ = unchecked(cellOut[1])
      const dx: f64 = <f64>(chunkX * 16 + 8 - originBlockX)
      const dz: f64 = <f64>(chunkZ * 16 + 8 - originBlockZ)
      const dist = Math.sqrt(dx * dx + dz * dz)
      if (dist > limit) continue
      count++
      if (dist < bestDist) {
        bestDist = dist
        bestX = chunkX
        bestZ = chunkZ
      }
      if (stopAt > 0 && count >= stopAt) {
        unchecked(scanOut[0] = count)
        unchecked(scanOut[1] = <i32>bestDist)
        unchecked(scanOut[2] = bestX)
        unchecked(scanOut[3] = bestZ)
        return count
      }
    }
  }
  unchecked(scanOut[0] = count)
  unchecked(scanOut[1] = count > 0 ? <i32>bestDist : -1)
  unchecked(scanOut[2] = bestX)
  unchecked(scanOut[3] = bestZ)
  return count
}

// Grid strongholds within radius. mode 0 = gated cells only (positions exact),

  const maxCellX = floorDiv(originChunkX + radiusChunks, SH_CELL) + 1

const MAX_RULES: i32 = 24
const rPlacement = new StaticArray<i32>(MAX_RULES)

let ruleCount: i32 = 0

export function resetRules (): void {
  ruleCount = 0

// placement < 0 means "strongholds"; `mode` is only read for those.
export function addRule (placement: i32, minCount: i32, radiusChunks: i32, maxNearestBlocks: i32, mode: i32): i32 {
  if (ruleCount >= MAX_RULES) return -1
  unchecked(rPlacement[ruleCount] = placement)
  unchecked(rMinCount[ruleCount] = minCount)
  unchecked(rRadius[ruleCount] = radiusChunks)
  unchecked(rMaxNearest[ruleCount] = maxNearestBlocks)
  unchecked(rMode[ruleCount] = mode)
  return ruleCount++
}

// 1 when every rule passes. The first failure returns, so rule order is cost.
export function evaluate (seedLo32: u32, seedLo48: u64, originChunkX: i32, originChunkZ: i32): i32 {
  for (let i: i32 = 0; i < ruleCount; i++) {
    const placement = unchecked(rPlacement[i])
    const minCount = unchecked(rMinCount[i])
    const radius = unchecked(rRadius[i])
    const maxNearest = unchecked(rMaxNearest[i])
    const mode = unchecked(rMode[i])
    // A nearest-distance test needs the true nearest, so such a rule scans fully.
    const stopAt = maxNearest >= 0 ? 0 : (minCount > 0 ? minCount : 1)
    const count = placement < 0
      ? scanStrongholds(seedLo32, originChunkX, originChunkZ, radius, mode, stopAt)
      : scanPlacement(placement, seedLo32, seedLo48, originChunkX, originChunkZ, radius, stopAt)
    if (count < minCount) return 0
    if (maxNearest >= 0) {
      const nearest = unchecked(scanOut[1])
      if (nearest < 0 || nearest > maxNearest) return 0
    }
  }
  return 1
}

// Full detail for one placement at one seed, written to `out` (8 i32 words):
// [count, nearestDistance, chunkX, chunkZ, blockX, blockZ, gatedOrFlag, 0].
export function detail (seedLo32: u32, seedLo48: u64, originChunkX: i32, originChunkZ: i32,
  placement: i32, radiusChunks: i32, mode: i32, out: usize): i32 {
  const count = placement < 0
    ? scanStrongholds(seedLo32, originChunkX, originChunkZ, radiusChunks, mode, 0)
    : scanPlacement(placement, seedLo32, seedLo48, originChunkX, originChunkZ, radiusChunks, 0)
  const chunkX = unchecked(scanOut[2])
  const chunkZ = unchecked(scanOut[3])
  store<i32>(out, count)
  store<i32>(out + 4, unchecked(scanOut[1]))
  store<i32>(out + 8, chunkX)
  store<i32>(out + 12, chunkZ)
  store<i32>(out + 16, count > 0 ? chunkX * 16 + 8 : 0)
  store<i32>(out + 20, count > 0 ? chunkZ * 16 + 8 : 0)
  store<i32>(out + 24, 0)
  store<i32>(out + 28, 0)
  return count
}

// consecutive low-32 seeds.
export function bench (placement: i32, seedLo32: u32, originChunkX: i32, originChunkZ: i32,

    total += scanPlacement(placement, lo, <u64>lo, originChunkX, originChunkZ, radiusChunks, 0)
  }
  return total

## How the uncertain parts get settled

Two independent measurements, and a rule that a hypothesis dies on the first
contradiction:

1. **Ask the server.** `tools/worldgen-algo/capture-structures.js` runs
   `locate structure` for a list of seeds and records the answers verbatim. That
   is Mojang's generator answering, so it is ground truth for those seeds.
2. **Read the binary.** `tools/binary-analysis/scan-binary.py` finds the
   identifiers in `.rodata`, resolves which code references them (RIP-relative
   scan over real instruction encodings), and exposes the dword-store immediates
   that constructors use to fill a placement record. Ghidra then decompiles the
   referencing functions.
3. **Fit, then try to break it.** `fit-structures.js` takes a candidate
   (salt, spacing, separation, spread) and requires that it put a cell start
   exactly on every reported chunk, for every seed. One miss rejects it.

That is why the placeholder rows in `src/world/structures-data.js` carry
`evidence: 'unknown'`: a salt that has not survived step 3 is a guess, and this
project does not ship guesses as answers.

### The two sets that are not on the grid

Both are open, and both are open *for a measured reason* rather than for want of
trying.

**`mineshaft`** is a per-chunk set (`spacing 1, separation 0`): every chunk is a
candidate and something decides. The harness tests both shapes such a decision
can take:

* a threshold on a draw -- `accept if draw < t` (or `> t`), for draw indices 0-4,
  three seed families, both engines. It walks the resolver's ring order from each
  capture's origin and collects the values of every chunk the search had to
  reject. Result: **zero separating thresholds**. The reason is arithmetic: with
  thousands of rejected chunks the rejected values cover the whole unit
  interval, so no cut can separate them from 24 accepted values unless the gate
  is much sparser than a uniform draw allows -- which is itself the answer.
* a `raw % k == 0` gate for every k up to 512, same families and draws. Result:
  **no k accepts all 24 answers**, so the gate is not a modulo test either.

What is left is a condition that is not a function of the chunk's own placement
stream, i.e. the biome/height check, which is the same reason the grid sets are
only exact at the chunk level. `mineshaft` therefore waits on the biome layer.

**`stronghold`** uses the concentric-ring algorithm, not a grid, so the grid
harness is silent about it. `tools/worldgen-algo/fit-strongholds.js` measures the
shape of the data instead:

```
seed  chunk     blocks        radius(chunks)  angle(deg)
1     66,76     1058,1218     100.7            49.0
2     -20,-55   -318,-878      58.5          -110.0
7     -20,43    -318,690       47.4           114.9
12    41,-199    658,-3182    203.2           -78.4
```

The nearest stronghold to the origin is 47-203 chunks out, which already
contradicts Java's first ring (128 chunks +/- 20). A parameterized ring model
(java/MT engine, base 4 or 6 rings, distance 8-64, spread 0-3, tolerance 7-64
chunks) explains at best 6 of 12 captures, i.e. chance. The harness prints the
tolerance it needed, so "fits with a huge tolerance" cannot be mistaken for a
fit. Cracking this needs the ring enumeration itself (`StrongholdFeature::vslot5`
/ `vslot6`), which is next.

### The two engines

`d2d2570` and `d2d2c60` are two placement resolvers, and they take different
arguments:

| resolver | arguments | mix |
|---|---|---|
| `d2d2570` | separation, spacing, spread type, salt, seed, cell pair | `(cellX*341873128712 + cellZ*132897987541 + seed + salt) ^ 0x5deece66d`, i.e. a Java LCG seed |
| `FUN_0d351a10` | the same, plus a per-level offset, and a ring search | `cellZ * -0xea9a42b + cellX * -0x66c60af8 + salt + seed` in 32 bits, then MT19937 |

The two multipliers in the second row are exactly the first row's constants
truncated to 32 bits (`341873128712 = 0x4F9939F508`, so `-0x66c60af8` mod 2^32 is
`0x9939f508`); the same identity holds for the Z constant. One arithmetic
family, two random engines.

`FUN_0d351a10` also shows *how* `locate` searches: it walks square rings of
cells outward from the origin cell (up to 100 rings), asks each cell for its
placement, and returns the first one the per-structure validity check accepts.
That is why a capture taken from `2048,2048` can name a structure whose cell is
not the one containing the reported chunk: the rings are walked around the
*origin*, and the answer is the first cell that passes the biome/height gate.

### What the reported position is

The chunk part is the placement chunk for every legacy set. For the two
pack-driven sets the answer is the jigsaw structure's own origin block: it sits
in the placement chunk or one chunk back on either axis, and for a corridor as
long as a trail ruin it can sit further along the corridor (one capture is 21
chunks out in Z). Predicting those exactly means running the jigsaw assembly,
which is a separate piece of work; the placement chunk underneath it is exact.

A second measurement from the same pass is about the within-chunk part: it is
constant per type. `village` is at `+8,+8` in 35 of 35 captures, `shipwreck` at
`+8,+8` in 24 of 24, `trial_chambers` at `+7,+7` or `+9,+9`, `trail_ruins` at
`+3,+3` for most captures. So the answer is a block position anchored inside the
placement chunk, and the chunk is what the resolver computed.

### Strongholds are a cell grid with a twist (2026-10-24)

Strongholds are not a ring walk in this build. The ring harness in
`tools/worldgen-algo/fit-strongholds.js` cannot explain them (it tops out at
3 of 6 from the origin at any tolerance up to 64 chunks), and the Java ring
radii are refuted outright by the captured sets: the strongholds of one seed sit
at 58, 179, 277, 338, 355, 503 chunks, which is no ring Java produces.

The real placement is a 200-chunk cell grid like every other set, with two
differences that make it look like a ring if you only look at positions:

1. the cell is 200 chunks wide, four times the widest legacy spacing; and
2. the seed mix folds the *cell centre*, `cell * 200 + 100`, not the cell index.

```
cellX  = floor(chunkX / 200)                       chunks, floored
u      = cellX * 200 + 100                         the cell centre
v      = cellZ * 200 + 100
seed32 = u * 0x9babeb51 + v * 0xbe68aeb9 + seed + 0x5d534e7      (mod 2^32)
```

`seed32` seeds a 32-bit Mersenne Twister and three draws come out of it:

| draw | use |
| --- | --- |
| 1 | `nextInt(100)` — the x jitter |
| 2 | `nextInt(100)` — the z jitter |
| 3 | `nextUInt() / 2^32` — compared against 0.25; see the tally below |

so the grid position is `cell * 200 + 50 + jitter` per axis. That is the `divps` by 200 at `0x4e9f094`, the `pmuludq` against
the two multipliers at `0x13e4220` / `0x13e8740`, the `add $0x5d534e7` at
`0x4e9f12a`, the two virtual `nextInt(100)` calls at `0x4e9f234` / `0x4e9f249`
and the `ucomiss` against the `0.25f` at `0x1098630`.

Three captured sets, one fitted on and two held out, give this tally
(`node tools/worldgen-algo/verify-strongholds.js`, no `--slug` means the whole
corpus):

| capture set | strongholds | on the predicted chunk | gated cells | of those, exact | ungated, exact |
| --- | --- | --- | --- | --- | --- |
| `stronghold_enum` (fit) | 32 | 17 | 20 | 17 | **0** |
| `stronghold_enum2` (fit, origin region) | 42 | 30 | 32 | 30 | **0** |
| `stronghold_enum3` (held out, untouched region) | 23 | 22 | 23 | 22 | **0** |
| all, when this table was written | 114 | 74 | 82 | 74 (90%) | **0** |
| all, current corpus (`verify-strongholds.js`) | **592** | **491** | **510** | **491 (96.3%)** | **0** |

So the gate is a *necessary* condition, with no counter-example in 592 captures,
and a *sufficient* one 96.3% of the time. The exceptions are strongholds whose
cell was gated in but whose position the generator still moved, so they are
reported as `gated: true` with a note rather than claimed as exact -- the flag is
the right answer for them, and `verify-strongholds.js` prints the running split
so the table cannot go stale in one direction only. The held-out region is where
the model does best, which is what a terrain-dependent relocation should look
like: the origin region is the one that has oceans in it.

What happens to the other three quarters of the cells is now readable in the
binary too. `0x4e9fca0` loads a provider out of the feature's own state
(`+0x1a8`), calls slot 6 of its vtable with the candidate position, and the
provider both decides *whether to reject* the cell and *rewrites the position*:
the value it leaves in that slot is what gets re-snapped to a cell and re-seeded.
That is a biome query, and it is why the relocated strongholds are not on the
200-chunk grid at all: `(84, 9)` cannot be `cell * 200 + 50 + [0..100)` for any
cell, on either axis, so no amount of jitter explains it. Predicting those
positions needs the biome layer, which is the next milestone; what is known today
is that each cell carries exactly one stronghold (592 captures, no cell holds two)
and a quarter of them are pinned exactly.

`src/world/stronghold.js` implements the grid, the mix and the gate, and
`tools/worldgen-algo/verify-strongholds.js` replays the captures and prints both
numbers separately, so a relocated stronghold is never counted as a hit.

### The gate decides existence, and that is measured (2026-10-25)

A sweep that walks a rectangle only finds out what is nearest to a grid of
origins. To test the model itself, `tools/worldgen-algo/plan-stronghold-probe.js`
builds a plan whose origins *are* the model's predictions: 40 cells per seed
whose gate draw is below 0.25 and which no capture had seen, plus 40 cells above
it as controls. An origin sitting on a stronghold makes `/locate` answer that
very chunk, so the answer is the model's own claim read back from the server.

`node tools/worldgen-algo/verify-probe.js` over 4 seeds (320 probes):

| cells | answered with the origin chunk itself |
| --- | --- |
| gated (draw < 0.25) | **159 / 160** (99.4%) |
| ungated (draw >= 0.25) | **0 / 160** |

So the gate is not a cosmetic flag: it is whether the cell holds a stronghold at
its grid position. The one gated miss is reported rather than smoothed away, and
the blind corpus above finds 19 of them in 510 gated cells: same phenomenon, a
larger sample, and the reason `gated` is offered as a necessary condition rather
than as a guarantee.

Two further measurements fell out of the same captures:

* **Only the low 32 bits of the seed reach the grid**, and the seed is carried
  exactly. Measured on captured worlds:

  | seed | shares its grid positions with | why |
  | --- | --- | --- |
  | `1` | `4294967297` (2^32+1) | same low 32 bits |
  | `9223372036854775807` | `-1` | 2^63-1 is 0xFFFFFFFF in the low word |
  | `0` | `4294967296` (2^32) | both are 0 in the low word |

  That is what `seed32` in `stronghold.js` implements, and why it is done in
  BigInt with a decimal-string entry point: a `Number() >>> 0` is wrong above
  2^53, which is exactly where the int64 seeds live, and the earlier capture
  run had already rounded `9223372036854775807` to `...76000` before the world
  was created.
* **A second, near-spawn population exists.** Of the strongholds `/locate`
  answers with, some are not any cell's grid position. Grouping every captured
  answer by distance from the origin shows they are not scattered:

  | distance from spawn (chunks) | strongholds | not on the grid |
  | --- | --- | --- |
  | 0-100 | 7 | **7 (100%)** |
  | 100-200 | 26 | 18 (69%) |
  | 200-300 | 16 | 12 (75%) |
  | 300-450 | 31 | 5 (16%) |
  | 450-600 | 23 | 3 (13%) |
  | 900-1500 | 12 | **0 (0%)** |

  Those positions are inside a 200-chunk cell but 50-350 chunks from its grid
  position, so no jitter explains them, and they change when only the high half
  of the seed changes (`1` vs `2^32+1` differ exactly there) — so that placement
  reads the full 64-bit seed, i.e. it is driven by the biome/climate data. The
  grid does not.

  `node tools/worldgen-algo/near-spawn-strongholds.js` counts them per seed and
  finds **exactly three** for every clean seed probed, at radii of 58-662
  chunks and arbitrary angles — a fixed small set near spawn, not a second grid.

  They are **all at villages**. Matching each one against the model's village
  list gives a hit for every single case: 39 of 39 off-grid strongholds across
  20 seeds sit exactly on a village chunk. The village grid is exact, so their
  positions are known; what is not known is *which* villages are chosen.

  A probe that put an origin on 800 modeled villages per seed settled the rate:
  2400 labelled villages contained exactly **3 village strongholds per seed**,
  all 7 that were re-probed answered their own chunk, and 2393 did not. Against
  those labels these candidates are all refuted (no single cut separates the
  positives from 2393 negatives):

  * a threshold gate on 12 draws x 8 cell sizes x 15 salts of the village cell's
    Mersenne stream, and of a per-chunk stream;
  * "nearest village" to the cell's grid position, its centre, each corner, its
    edges, and to 3 hidden points decoded from further draws of the same stream
    (0-2 of 52 cases, i.e. chance);
  * rank in generation order, radius, and chunk-coordinate residues.

  So the selection is not a per-village gate and not a nearest-village snap. It
  reads the full 64-bit seed (only the residue-driven part does not), and the
  counts are fixed at three per world. That is the one gap left in stronghold
  placement, and it is isolated to a 3-element set whose candidate positions are
  already known exactly.

`node tools/worldgen-algo/verify-locate.js` is the acceptance harness for this:
it replays every captured `/locate` question and classifies the answer as
`exact`, `relocated` (a position that is no cell's grid position) or `wrong`
(the server named a grid position that was not the model's nearest). The current
tally over 4708 queries is 2779 exact (59.0%), 1883 relocated, 46 wrong — the
`wrong` count is the one that has to be driven to zero, and it is 1.6% of the
queries whose answer is on the grid at all.

### Why the binary has to be read where it runs

The release asset is on a host this working environment cannot reach
(`www.minecraft.net` and `release-assets.githubusercontent.com` both fail at
connect, and no npm or PyPI package ships the server), so the binary is only ever
available inside CI. That is enough to run it (captures, memory dumps) and enough
to read it (`objdump`/Capstone over published slices), but it makes every
measurement that needs the file a round trip. The pipeline therefore publishes
what it reads: `binary-sections/` holds `.rodata`, `.data.rel.ro`, `.data` and the
`.text` window that contains every structure-name reference, each with its
virtual address, so the static side of this work can be repeated from a checkout.

## Honest limitations

- **Placement is reproduced for eleven sets.** Eight are exact for every captured
  position; `trail_ruins` and `trial_chambers` are within a chunk and are limited
  by the jigsaw-origin convention described above, not by the grid. Strongholds
  are exact for the cells whose gate draw is below 0.25 (30 of 32 measured), and cell-exact
  for the rest, whose position comes out of a biome query that is not modelled
  yet. Re-run `node tools/worldgen-algo/verify-placements.js` and

- **Six sets still have no measured row**: ocean ruins, desert pyramids, jungle
  temples, witch huts, igloos, abandoned camps. Their shape is known
  (`placeholder` rows say so) and nothing pretends otherwise.
- **`mineshaft` and `stronghold` are not grids at all, and both are still open.**
  Mineshafts are a per-chunk decision, and the harness has refuted every
  draw-based shape of it (threshold and modulo, three seed families, both
  engines), which points at the biome/height check rather than a new random.
  Strongholds use concentric rings; the captures contradict Java's ring radii
  (nearest stronghold 47-203 chunks out) and no parameterized ring model in the
  family the harness searches explains them. Strongholds turned out not to be
  rings at all -- they are a 200-chunk cell grid with a gate (see above) -- so
  what is left open for them is the biome query, and for mineshaft the
  biome/height test. Both need the biome layer this repository does not have yet.
- **A set's reported position is not always its placement chunk.** For the
  pack-driven sets it is the structure's own origin block, which can sit one
  chunk back on either axis (and further, along a corridor). The model reports
  the placement chunk and the tools keep the residual visible instead of hiding
  it inside a symmetric tolerance.
- **A quarter of the strongholds are exact, the rest are cell-exact.** The
  stronghold grid, mix and gate are modelled; what a cell's non-gated stronghold
  position is comes from the biome provider, so until biomes are modelled those
  are reported as `gated: false` rather than given a made-up position.
- **Terrain blocks are not predicted.** The noise primitive is exact, but the
  router that decides which noises to sample, and the splines that turn climate
  into density, are not wired up.
- **Biome assignment is not implemented**, although the climate target points
  each biome occupies are loaded and available.
