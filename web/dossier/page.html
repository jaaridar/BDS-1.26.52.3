1. The algorithm, completely

Bedrock's structure placement answers one question: given a 64-bit world seed, which chunks contain the start of structure set S? It does it in two stages — a candidate grid, which is pure arithmetic, and a per-structure gate, which asks the world's biome and height data whether the candidate is allowed. The grid is fully recovered. The gate is recovered only for strongholds, and for the rest the model reproduces every captured answer anyway, because the gate rejects candidates rather than moving them.

1.1 Coordinates and the seed reduction

Two coordinate systems are in play and they are never mixed: chunks (16 blocks) and blocks. A structure start is computed in chunks and reported as the block at the chunk's centre, chunk × 16 + 8. Cell indices are floor(chunk ÷ spacing), with Java's floor (towards negative infinity), not truncation.

A world seed is 64 bits, and the two placement engines read different parts of it:

seed32 = low 32 bits of the seed (mod 2^32, two's complement) seed48 = low 48 bits of the seed (mod 2^48) The Mersenne engine folds its cell seed into 32 bits, so it sees only seed32. The Java engine masks its LCG state to 48 bits, so it sees only seed48.

Consequence, measured: seeds s and s + 232 place every Mersenne-engine set identically, and seeds s and s + 248 place every Java-engine set identically. The self-checks below re-derive this on your machine rather than asking you to believe it.

1.2 The Mersenne stream

Both engines start from a Mersenne Twister seeded with init_genrand: 624 words of state, multiplier 1812433253, tempering masks 0x9d2c5680 and 0xefc60000. The two draw conventions are not part of the published algorithm, so they were measured rather than assumed:

next32() = one tempered 32-bit word nextInt(bound) = next32() mod bound (unsigned divide, no rejection) nextUnit() = f32( next32() × 2^-32 ) (integer → double → float)

The f32 narrowing matters: the gate compares against 0.25f, and a value a whisker above 0.25 can round down onto it. That case is implemented exactly, not approximately.

1.3 The candidate grid

Every set except strongholds uses the same resolver, with per-set numbers. A cell is spacing chunks wide and its candidate sits at least separation chunks inside it, so span = spacing − separation.

cellX = floor(chunkX ÷ spacing) cellZ = floor(chunkZ ÷ spacing) span = spacing − separation Mersenne engine: cellSeed = (cellX × 0x9939f508 + cellZ × 0xf1565bd5 + seed32 + salt) mod 2^32 state = MT19937(cellSeed) linear ox = next32() mod span oz = next32() mod span triangular ox = floor( (next32() mod span + next32() mod span) ÷ 2 ) oz = floor( (next32() mod span + next32() mod span) ÷ 2 ) Java engine: cellSeed = (cellX × 341873128712 + cellZ × 132897987541 + seed48 + salt) mod 2^64 state = (cellSeed XOR 0x5deece66d) mod 2^48 next(b) = state = (state × 0x5deece66d + 0xb) mod 2^48; return state ≫ (48 − b) linear ox = nextInt(span) oz = nextInt(span) triangular ox = floor( (nextInt(span) + nextInt(span)) ÷ 2 ) (same for z) start chunk = (cellX × spacing + ox, cellZ × spacing + oz) start block = (startChunkX × 16 + 8, startChunkZ × 16 + 8)

The two 32-bit multipliers are the low halves of the Java constants (341873128712 mod 2^32 = 0x9939f508, 132897987541 mod 2^32 = 0xf1565bd5): the binary multiplies in 32 bits, which is exactly a fold of the 64-bit mix.

1.4 Strongholds

Strongholds are not a ring walk in this build, and they are not jittered inside a cell. They sit on a 200-chunk grid, each cell carrying one stronghold, and the mix runs over the cell's centre rather than its index:

u = cellX × 200 + 100 v = cellZ × 200 + 100 cellSeed = (u × 0x9babeb51 + v × 0xbe68aeb9 + seed32 + 0x5d534e7) mod 2^32 state = MT19937(cellSeed) dx = next32() mod 100 dz = next32() mod 100 gate = f32( next32() × 2^-32 ) gridChunk = (cellX × 200 + 50 + dx, cellZ × 200 + 50 + dz)

The third draw is a gate, compared against 0.25, and what it decides is measured rather than assumed: it decides whether the stronghold ends up on that grid position. Every cell carries exactly one stronghold — no capture has ever shown two in one cell — but when the gate fails, the generator moves the stronghold, and the moved position comes out of a biome query that is not modelled here.

{{STRONGHOLD_EVIDENCE}}

There is a second population of strongholds that this grid cannot express: every world also contains exactly three strongholds at villages, at radii of 47 to 662 chunks from the origin. Their positions are exact, because they are village chunks and the village grid is exact — but which villages are chosen is not recovered, so they are listed as open below and are not reported by the calculator.

1.5 What a locate answer is

/locate structure walks cells outward from your position and returns the first candidate whose biome and height checks pass, with its distance. It does not enumerate and it does not sort globally, which is why two different origins can return two different "nearest" answers for the same structure. The model here reports the candidate grid, so it reproduces locate exactly when the accepted candidate is the grid candidate — which is the case for every captured answer of every set offered as a filter.

6. Forensic record: how each number was pinned

6.1 Method

Two independent sources were used, and a constant was only accepted when both agreed:

  1. Static: the shipped bedrock_server (Linux x86-64, version 1.26.52.3) was disassembled. Constants were read out of the instruction stream and the read-only section, and the call graph around the structure feature was mapped. Addresses are cited below so any reader can check them with objdump — nothing else here depends on trusting this paragraph.
  2. Dynamic: a real server, started once per seed, was asked /locate structure from a scripted set of origins. The answers are recorded with the seed they came from (research/proprietary/bds-1.26.52.3/structures/captures/, 1411 files) and replayed by the verifiers. A parameter set was accepted only when it reproduced every captured position of that set; a fit that needed a tolerance to reach a neighbouring chunk is reported as exactly that.

7. Hypotheses that were falsified

This is the part that keeps the rest honest. Each row is a model that looked plausible, the measurement that killed it, and what replaced it. All of them can be re-run from the repository.

Dead ends, with the number that ended them
Hypothesis Result What the data said instead
Strongholds walk Java's concentric rings (128 + 6·ring·32) 6 / 12 captures at best Chance. The nearest stronghold is 47–203 chunks out, which contradicts the first Java ring outright. Replaced by the 200-chunk cell grid.
The off-grid strongholds are a second 200-block grid 0 / 41 No second grid. The off-grid set is exactly three per world and every one sits on a modelled village chunk.
Strongholds are placed in block space, not chunk space 0 / 41 Chunk space. The grid formula reproduces positions to the block.
"The answer lies inside the origin's own 200-chunk cell" is a meaningful test 2 / 160 It is not: cells are large and the test passes about as often as the geometry predicts. It was dropped rather than quoted.
A cell's stronghold is the stronghold nearest a point hidden in that cell's Mersenne stream 5 / 52 Chance. 10×10 draw pairs × 3 target maps, all at chance level.
A cell's stronghold is the village nearest its grid position 0 / 52 The chosen village is a median of 78 chunks from the grid position (range 19–157), which rules out any snap-to-nearest geometry.
Villages carry a stronghold when a per-village random draw passes separation 0.0000 2400 labelled villages, 15 salts × 8 cell sizes × 12 draws, both the village cell stream and a per-chunk stream: no threshold separates the 7 positives from the 2393 negatives. Not a per-village gate.
The three village strongholds are simply the N nearest villages to spawn ranks 5 … 1188 No rank cut exists: the positives include the 1188th village and exclude the first. The count is fixed at exactly three per world, so it is also not a rate over villages.
Mineshafts are a spaced grid set with an unknown spacing no k No modulus accepts all 24 answers; this set is gated per chunk by the biome/height test, which is not modelled yet.

8. What is still open

  • Which villages carry the three strongholds. The positions are known (they are village chunks) and the count is known (exactly three per world), but the selection is not recovered: it is not a per-village random draw, not a nearest-village snap, not a rank cut, and not tied to the gated cells. It reads more of the seed than the grid does, which points at the biome layer — the same query that relocates the ungated cells. Everything ruled out is in §7 with its number.
  • 19 of the 510 gated strongholds. The gate is necessary and 96.3% sufficient; the remainder are cells the generator moved for a non-gate reason. They are reported as gated with a flag, never as exact.
  • Biomes and terrain. The climate noise router has not been recovered, so no surface biome, height or block can be predicted from a seed. The biome data — 76 biomes with their climate targets — is read from the packs, but data is not a sampler, which is why there is no biome filter in §4.
  • Seven sets with unmeasured placement: ocean ruins, desert pyramids, jungle temples, witch huts, igloos, mineshafts and abandoned camps. Their parameters are placeholders or their gate is a per-chunk probability whose threshold is unknown.
  • Obsidian and the rest of the structure itself. This file covers where a structure starts. Piece layout, jigsaw assembly, loot tables and block placement are separate systems and are not modelled.

9. Reproducing every number

Every claim in this file is produced by a command in the repository jaaridar/BDS-1.26.52.3. Node 22 or newer, no build step, no server needed for replay. 

# per-set tallies: captured positions replayed exactly / within one chunk
node tools/worldgen-algo/verify-placements.js

# strongholds: gated against ungated, exact against relocated, per capture set
node tools/worldgen-algo/verify-strongholds.js

# the probe sweep that asks the server about the model's own predictions
node tools/worldgen-algo/verify-probe.js

# one seed, every structure, with the evidence for each row
node tools/worldgen-algo/world.js --seed 12345

# the browser seed finder and its tests
node web/server.js                       # http://localhost:8787
node --test test/unit/seedfinder-wasm.test.js
node tools/web/a11y-check.js
node tools/web/smoke-web.js

# regenerate this file (needs the AssemblyScript compiler for the wasm core)
ASC=/path/to/asc.js node tools/web/build-dossier.js

To regrow the evidence rather than replay it, the capture harness asks a real server: tools/worldgen-algo/capture-structures.js starts the official binary, sends /locate commands from a plan of origins, and writes one JSON per capture set. Every plan used here is in .github/sweep/, and the sweeps run in CI on a fresh world so a stale world can never answer.

The capture corpora and the official binary itself are not in this file: they are derived from Mojang's software and are treated as proprietary in that repository (docs/licensing.md). What is in this file is the algorithm, the tallies it produces, and the code that recomputes them.
